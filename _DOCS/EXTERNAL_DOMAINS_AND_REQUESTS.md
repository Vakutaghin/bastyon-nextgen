# Внешние домены и запросы из старого приложения

## Обзор

Данный документ описывает все внешние домены и сервисы, к которым обращается старое приложение Pocketnet/Bastyon. Информация собрана на основе анализа кодовой базы старого приложения (`pocketnet.gui`).

## 1. Блокчейн-ноды (RPC API)

### Основные прокси-серверы (Production)

Приложение использует пул прокси-серверов для балансировки нагрузки и обеспечения отказоустойчивости:

- **1.pocketnet.app:8899** (WSS: 8099)
- **2.pocketnet.app:8899** (WSS: 8099)
- **3.pocketnet.app:8899** (WSS: 8099) - используется по умолчанию в новом приложении
- **4.pocketnet.app:8899** (WSS: 8099)
- **5.pocketnet.app:8899** (WSS: 8099) - используется в PHP-скриптах
- **6.pocketnet.app:8899** (WSS: 8099)

**Протоколы:**
- HTTPS на порту 8899 для RPC запросов
- WSS (WebSocket Secure) на порту 8099 для real-time обновлений

**Эндпоинты:**
- `/rpc/{method}` - стандартные RPC запросы
- `/rpc-ex/{method}` - расширенные RPC запросы (с опцией `ex: true`)

**Использование:**
- Все запросы к блокчейну проходят через эти прокси
- Приложение автоматически переключается между серверами при ошибках
- В новом приложении (`bastyon-vue`) используется сервер `3.pocketnet.app` по умолчанию

### Тестовая сеть (Testnet)

- **test.pocketnet.app:8899** (WSS: 8099)

### Прокси для переводов

- **2.pocketnet.app:8899** - используется для запросов перевода

## 9. IPFS (InterPlanetary File System)

Приложение поддерживает работу с IPFS для децентрализованного хранения контента.

**Формат URL:**
- `/ipfs/{hash}` - доступ к контенту через IPFS

**Использование:**
- Хранение видео и медиа-файлов в децентрализованной сети
- Распределенное хранение контента
- Устойчивость к цензуре

**Примечание:** Конкретные IPFS gateway домены не указаны в коде, вероятно используются публичные gateway или встроенные в ноды.

## 13. Архитектура запросов

### Схема работы с блокчейном

```
Клиент → Прокси-сервер (1-6.pocketnet.app:8899) → Блокчейн-нода → Блокчейн
```

### Схема работы с медиа

```
Клиент → Сервер загрузки (pocketnet.app:8092) → Хранилище
Клиент → Peertube сервер → Видео контент
Клиент → IPFS Gateway → IPFS сеть
```

### Схема работы с чатом

```
Клиент → Matrix сервер (matrix.pocketnet.app) → Децентрализованная сеть Matrix
```

## 14. Безопасность и приватность

### HTTPS/WSS

Все основные соединения используют защищенные протоколы:
- HTTPS для RPC запросов
- WSS для WebSocket соединений

### Аутентификация

- RPC запросы могут требовать подписи (при `auth: true`)
- Используется криптографическая подпись на основе приватного ключа пользователя
- API ключи для некоторых сервисов (загрузка изображений, переводы)

### Обход блокировок

- Tor Snowflake bridges для обхода блокировок
- Множественные прокси-серверы для балансировки
- Распределенная сеть Peertube серверов

## 15. Рекомендации для нового приложения

### Конфигурация

1. **Централизованная конфигурация серверов:**
   - Использовать `servers.json` для управления списком серверов
   - Поддержка переключения между production и testnet

2. **Балансировка нагрузки:**
   - Реализовать автоматическое переключение между прокси-серверами
   - Обработка ошибок и retry логика

3. **Кеширование:**
   - Кеширование информации о нодах (как в старом приложении - 55 секунд)
   - Кеширование OpenGraph метаданных

4. **Мониторинг:**
   - Отслеживание доступности серверов
   - Метрики времени ответа
   - Логирование ошибок подключения

### Безопасность

1. **Валидация сертификатов:**
   - Проверка SSL/TLS сертификатов
   - Защита от MITM атак

2. **Управление ключами:**
   - Безопасное хранение приватных ключей
   - Использование аппаратных кошельков где возможно

3. **Приватность:**
   - Минимизация данных, отправляемых на внешние сервисы
   - Использование Tor для чувствительных операций

### Производительность

1. **Оптимизация запросов:**
   - Батчинг RPC запросов где возможно
   - Использование WebSocket для real-time обновлений

2. **CDN и кеширование:**
   - Использование CDN для статических ресурсов
   - Кеширование медиа-контента

3. **Ленивая загрузка:**
   - Ленивая загрузка изображений и видео
   - Виртуализация списков для больших объемов данных

## 16. Зависимости от внешних сервисов

### Критические зависимости

- **Блокчейн-прокси (1-6.pocketnet.app)** - критично, без них приложение не работает
- **Matrix серверы** - критично для чата
- **Серверы загрузки изображений** - критично для загрузки медиа

### Важные зависимости

- **Peertube серверы** - важно для видео функциональности
- **Сервисы перевода** - важно для мультиязычности
- **OpenGraph парсер** - важно для превью ссылок

### Опциональные зависимости

- **Внешние видео-платформы** - опционально, только для встраивания
- **CDN сервисы** - опционально, можно использовать альтернативы
- **Tor bridges** - опционально, только для обхода блокировок

## 17. Миграция на новое приложение

При миграции на новое Vue приложение (`bastyon-vue`) необходимо:

1. **Сохранить совместимость:**
   - Использовать те же домены и порты
   - Сохранить формат RPC запросов
   - Поддержать существующие API ключи

2. **Улучшить архитектуру:**
   - Централизовать конфигурацию серверов
   - Улучшить обработку ошибок
   - Добавить retry логику

3. **Оптимизировать производительность:**
   - Использовать современные технологии (HTTP/2, WebSocket)
   - Реализовать эффективное кеширование
   - Оптимизировать размер запросов

## Заключение

Старое приложение использует распределенную архитектуру с множеством серверов для обеспечения отказоустойчивости и производительности. При миграции на новое приложение важно сохранить эту архитектуру и улучшить её там, где это возможно.

Основные принципы:
- **Децентрализация** - множественные серверы для каждого сервиса
- **Отказоустойчивость** - автоматическое переключение при ошибках
- **Приватность** - использование Tor и шифрования
- **Производительность** - кеширование и оптимизация запросов
