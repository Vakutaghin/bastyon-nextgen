## 1. Безопасность: закрыть выпуском 0.9.1

Все три дыры есть в опубликованной v0.9.0 (29.09.2026).

### 1.1 Сообщение LXMF с неверной подписью показывается как настоящее

**Сейчас.** Узел сообщает, сошлась ли подпись сообщения: поле `signed` в событии `message`
(`bastyon-rns/src/node.rs`, `message_event`). Фронт это поле не читает: `receiveLxmf` в
`mesh-chat-store.ts` принимает любое сообщение. Ни lxmf-rs, ни Python LXMF такие сообщения не
выбрасывают — решать должен клиент. Sideband и NomadNet их помечают.

Отправителя в LXMF удостоверяет только подпись: адрес отправителя в сообщении — просто поле.
Отсюда два следствия:

- в обычный LXMF-чат сообщение «от» любого адреса может прислать кто угодно, кто знает мой адрес
  (он есть в announce);
- в чате Bastyon с маршрутом подделку покажут как сообщение собеседника. Для этого нужно знать
  оба адреса LXMF и чьи они — например, это знает общий знакомый, которому оба дали адреса.

**Сделать.**

- Узел отдаёт три состояния вместо флага: подпись верна, неверна, отправитель неизвестен
  (`signature_valid`: `Some(true)`, `Some(false)`, `None`).
- Неверная подпись — сообщение не показывать, только строка в журнале узла.
- Отправитель неизвестен (его announce ещё не приходил) — показывать в LXMF-чате с пометкой
  «отправитель не проверен», в чат Bastyon не подмешивать. Ключ собеседника с маршрутом узел уже
  знает (`rns_learn`), так что у него такого случая быть не должно.
- Запись связки из полей `0xFB/0xFC` принимать только из сообщения с верной подписью.

**Проверка.** Rust-тест события на три состояния. Юнит-тесты стора: сообщение с неверной
подписью не показано, от неизвестного — с пометкой и не в чате Bastyon. e2e маршрута с подложенным
событием.

**Объём.** 1 день.

### 1.2 Ключ собеседника Meshtastic меняется молча

**Сейчас.** Ключ для ЛС собеседника (PKI) берётся из последнего NodeInfo и перезаписывается без
предупреждения (`mesh-chat-store.ts`, `peerPublicKey` в `syncMeshtasticPeers` и `ingest`). Номер узла в Meshtastic ничем не защищён: чужое радио может назваться номером
собеседника и прислать свой ключ. После этого ЛС «собеседнику» шифруются на ключ чужого радио.

**Сделать.**

- Первый ключ собеседника запомнить. Если ключ сменился — сказать об этом в чате («ключ
  собеседника изменился») и не отправлять в этот диалог до подтверждения.
- У собеседника с маршрутом верный ключ — из записи связки: её подписал его аккаунт. NodeInfo с
  другим ключом для него не принимать, радио заново отдать ключ из записи (`add_contact`), в чате —
  предупреждение.

**Проверка.** Юнит-тесты стора. Прогон против `meshtasticd`: третий узел с тем же MAC (`-h`), то
есть с тем же номером, но своим ключом, выдаёт себя за второй. Предупреждение появляется, ЛС на
новый ключ не уходят.

**Объём.** 1–2 дня.

### 1.3 Файл NomadNet без предела размера

**Сейчас.** Ответ-ресурс принимается без проверки размера: в вендоренном
`rns-net/src/common/link_manager.rs` у ответов нет проверки при приёме. Файл до сохранения целиком
лежит в памяти, ограничен только час на скачивание. Узел NomadNet может отдать файл на несколько
гигабайт и одной ссылкой выбить приложение по памяти.

**Сделать.** Проверять размер до начала передачи: он есть в объявлении ресурса. Выше предела (по
умолчанию 100 МБ) — спросить. Запись на диск по частям — пункт 5.1.

**Проверка.** Rust-тест: `peer.py` отдаёт файл больше предела — ресурс отклонён, память не растёт.

**Объём.** Полдня.

## 3. Мессенджер: один диалог, несколько маршрутов

### 3.1 Вложения, голос, ответы и реакции через маршрут

**Сейчас.** Через mesh уходят только текст и повтор текстового сообщения (`messenger-store.ts`,
`sendMessage` и `retryMessage`). Ответы, реакции, голосовые, картинки, видео, файлы и PKOIN
уходят только через Matrix: без сервера они не доходят. Кнопки в чате при этом активны
(`chat-room.vue`). Ссылка IPFS уходит обычным текстом, то есть через mesh тоже.

**Сделать.** Что умеет сеть маршрута, то и уходит через неё. Остальное честно недоступно.

- **Reticulum:**
  - картинки, файлы и голос — как в LXMF-чате: `rns_send` это уже умеет, картинка уменьшается до
    900 КБ;
  - ответы и реакции — полями LXMF 1.1 (пункт 4.3);
  - ответ на сообщение, пришедшее через Matrix, — цитатой (`FIELD_REPLY_QUOTE`): у такого
    сообщения нет хэша LXMF.
- **MeshCore и Meshtastic** — только текст:
  - Meshtastic — ответы и реакции своими полями (`reply_id`, `emoji`), как в mesh-чате;
  - MeshCore — ответ цитатой в тексте;
  - голос, файлы и PKOIN — кнопки неактивны с подсказкой «через радио уходит только текст».
- PKOIN через mesh не уходит ни в одной сети: переводу нужна блокчейн-нода.

**Как.** `activeMeshRoute` отдаёт возможности сети маршрута: вложения, ответы, реакции, предел
байт. Композер и меню сообщения смотрят на них, а не на тип сети. Это `ChatTransport` из раздела
6.1 анализа, но без переноса Matrix за адаптер. Отправка идёт через mesh-диалог маршрута теми же
функциями, что в `mesh-chat-room`.

**Проверка.** e2e без сервера: голосовое, картинка, ответ и реакция уходят через Reticulum.
interop-тест: у Python-собеседника нужные поля. На радио-маршруте кнопки голоса и файлов
неактивны.

**Объём.** 4–6 дней, без 4.3.

### 3.2 История через mesh — в Matrix, когда связь вернулась

**Сейчас.** Переписка через mesh хранится только на этом устройстве (справка, «Ограничения»).
Когда сервер возвращается, в истории Matrix остаётся дыра. На втором устройстве и после
переустановки этих сообщений нет, а при выходе из аккаунта они стираются.

**Сделать.** Одна история чата на всех устройствах обоих собеседников.

**Как.**

- Каждый копирует на сервер только свои сообщения, отправленные через mesh. Так у двух сторон нет
  встречных дублей.
- Копия — обычное зашифрованное сообщение Bastyon с меткой `bastyonMeshCopy: { net, id, ts }`:
  - `id` — тот же ключ, по которому mesh-история убирает повторы (`uniq`: хэш LXMF или id пакета
    радио);
  - `ts` — когда сообщение ушло через mesh.
- Копия, чей `id` уже есть в локальной mesh-истории получателя, второй раз не показывается.
  Остальные копии (например, на другом устройстве) встают в ленту по `ts` с пометкой «через
  Reticulum», «через MeshCore» или «через Meshtastic».
- Копии уходят пачкой после первого синка, по порядку времени. Очередь неотправленных копий лежит
  в IndexedDB рядом с mesh-историей и переживает перезапуск.
- Вложения копируются обычной загрузкой Bastyon.
- Если человек сам выбрал «через mesh», когда сервер был доступен, копий нет: он сознательно не
  хотел отдавать это серверу.
- Старый клиент покажет копию как обычное сообщение, то есть с дублем. Это допустимо.

**Проверка.** e2e: переписка без сервера → сервер вернулся → копии ушли. У собеседника дублей
нет. Второй вход в тот же аккаунт (другой профиль браузера) видит всю историю по порядку времени.

**Объём.** 5–7 дней.

### 3.3 Маршруты под управлением и отзыв адреса

**Сейчас.** Маршрут видно только в полосе внизу чата. Удалить маршрут собеседника нельзя:
есть только полный сброс при смене аккаунта. У записи связки нет ни срока, ни отзыва: новая запись
той же сети просто заменяет старую.

Это вопрос безопасности. В Meshtastic и MeshCore сообщения расшифровывает радио, ключи лежат на
нём. Потерянное или украденное радио продолжит получать ЛС от всех, у кого есть мой маршрут, пока
нет сервера. Сейчас это не отозвать: можно только подключить новое радио и снова разослать адреса.

**Сделать.**

- В профиле собеседника или в меню чата — его маршруты: сеть, адрес, когда получен, подписан ли
  самим радио. Кнопка «Забыть маршрут».
- В «Моих адресах в mesh-сетях» — кому разослан адрес и «Отозвать» для каждой сети.
- Запись отзыва: текст `bastyon-mesh-revoke/1`, сеть, адрес Bastyon, время; подпись аккаунта.
  - Получатель удаляет маршрут этой сети, если запись связки старше отзыва, и такие записи больше
    не принимает.
  - Отзыв рассылается там же, где запись связки: в Matrix всем, кому был разослан адрес, и полем
    LXMF.
- Срок у записи связки не ввожу: без сервера новую получить неоткуда, и старый маршрут лучше, чем
  никакого.

**Проверка.** Юнит-тесты `binding.ts`: подпись отзыва; чужой отзыв не действует; отзыв старше
записи не действует. Юнит-тесты стора. e2e: после отзыва маршрут у собеседника пропадает, и
отправка без сервера невозможна с понятным объяснением.

**Объём.** 3–4 дня.

### 3.4 Обмен адресами без ручного шага

**Сейчас.** Поделиться адресами можно только вручную: пунктом в меню 📎 или кнопкой «Поделиться
своим» под полученной записью. Автоматически уходит только запись Reticulum — к первому
LXMF-сообщению в запуске и только тому, чей маршрут уже известен. Адреса радио сами не
рассылаются. Кнопка «Поделиться своим» требует запущенного Reticulum, даже когда подключено только
радио (`message-item.vue`, `canShareBack`), — это ошибка.

Маршрут нужен, когда интернета уже нет, а обменяться адресами надо было раньше. Большинство людей
не станет вручную рассылать их каждому собеседнику.

**Сделать.**

- Настройка «Делиться адресами в mesh-сетях с собеседниками», по умолчанию выключена. После
  включения служебное сообщение с записями уходит во все личные чаты с перепиской за последние
  90 дней. После смены радио туда же уходит новая запись.
- Ответная рассылка: если настройка включена, приложение отвечает собеседнику своей записью на
  его запись.
- Кнопке «Поделиться своим» достаточно любой подключённой сети.

Почему по умолчанию выключено:

- адрес LXMF показывает, когда я в сети;
- номер узла Meshtastic указывает на конкретное радио, а радио можно запеленговать.

**Объём.** 2–3 дня.

### 3.5 Сквозное шифрование через радио для чатов Bastyon

**Сейчас.** Маршрут через Meshtastic или MeshCore везёт текст открытым до радио. Радио
расшифровывает его, и прочитать может любой, кто подключён к радио по BLE или TCP. В разделе 4
анализа это отложено как «усиленный режим».

**Сделать.** Сообщения между двумя пользователями Bastyon через радио шифрует приложение, а радио
везёт уже шифротекст. Тогда чат Bastyon остаётся сквозным и без сервера.

**Как.**

- Ключ — ECDH secp256k1 между ключами аккаунтов (оба есть в записях связки), затем HKDF с меткой
  сети.
- Шифр — AEAD ChaCha20-Poly1305. На сообщение уходит 24 байта: 8 случайных байт nonce и 16 байт
  тега. Счётчик вместо случайного nonce не годится: у аккаунта может быть несколько устройств.
- Meshtastic — двоичный пакет в `PRIVATE_APP` (256). Официальное приложение его не покажет, и это
  правильно.
- MeshCore — текст в base64, около 100 байт полезного на сообщение. Двоичные способы прошивки —
  проверить по исходнику, доходят ли они до приложения собеседника.
- Forward secrecy нет: ключи статические. В интерфейсе такой чат помечен «шифрование Bastyon», без
  оговорки про радио.

**Проверка.** Юнит-тесты шифра и разбора. Прогон против двух `meshtasticd`: в журнале узла только
шифротекст.

**Объём.** 4–6 дней.

### 3.6 Несколько устройств одного аккаунта

**Сейчас.** Identity Reticulum выводится из ключа аккаунта, поэтому адрес LXMF одинаков на всех
устройствах, и устройства никак не договариваются между собой. Прямая доставка уходит туда, куда
ведёт последний announce. Забор с узла доставки удаляет сообщения на узле, и второе устройство их
уже не получит. История на каждом устройстве своя.

**Сделать и как.**

- Напрямую принимает одно устройство. Настройка «Принимать сообщения Reticulum на этом
  устройстве»: на остальных узел не объявляет адрес доставки и не удаляет почту на узле доставки.
- Если узел видит announce своего же адреса из сети, значит, работает другое устройство, — сказать
  об этом. Отдаёт ли rns-net такие announce, надо проверить.
- Остальные устройства видят историю через копии в Matrix (3.2).
- Ratchets (4.2) делать с учётом этого: если у двух устройств один адрес и разные ratchet, одно не
  прочитает то, что зашифровано для другого.

**Объём.** 3–5 дней, без 3.2.

### 3.7 Групповые чаты через mesh

**Сейчас.** Маршруты есть только у личных чатов. У группы в поле собеседника — id комнаты, а не
адрес (`use-dialog-mapping.ts`; `routeOf` в `use-mesh-routes.ts`).

**Сделать.** Группа Bastyon продолжает работать без сервера.

**Как.**

  своих полях (`0xFB/0xFC`, тип `bastyon.group/1`). Годится для групп примерно до 20 человек: по
  радио каждое сообщение — это N передач.
- **MeshCore.** У группы свой приватный канал. Создатель генерирует секрет на 16 байт и отдаёт его

- В канале автор определяется по имени радио, а не по аккаунту. В интерфейсе так и написать:
  «автор не проверен».

**Проверка.** e2e с поддельным MeshCore и двумя Python-собеседниками LXMF.

**Объём.** 1,5–2 недели.

## 4. Reticulum

### 4.1 Автосинхронизация с узлом доставки

**Сейчас.** Сообщения с узла доставки забираются только кнопкой «Получить сообщения»
(`rns-propagation.vue`). Фоновый цикл узла обрабатывает задания, интерфейсы и announce раз в 6
часов, но почту не забирает. При старте узел только запрашивает путь к узлу доставки. На Android
так же. Телефон без нажатия кнопки не узнает о сообщениях, пришедших, пока он был не в сети.
Sideband забирает их сам.

**Сделать.** Забирать почту:

- при старте, когда путь к узлу доставки найден;
- по таймеру: выкл, 15, 30 или 60 минут, 6 часов; по умолчанию 30 минут;
- когда появилась сеть (поднялся интерфейс).

Если из интерфейсов только RNode, по умолчанию раз в 6 часов: эфир дорогой. На Android — внутри
службы, пока узел работает. После неудачи пауза растёт.

**Проверка.** interop-тест: Python-собеседник шлёт через узел доставки, пока узел Bastyon
выключен. Узел Bastyon стартует, и сообщение приходит без кнопки.

**Объём.** 1–2 дня.

### 4.2 Ratchets: forward secrecy для сообщений ко мне

**Сейчас.** Свой адрес `lxmf.delivery` объявляется без ratchet-ключа: вендоренный rns-net собирает
announce без ratchet, а lxmf-rs (`announce_delivery`) его не заводит. Поэтому одиночные сообщения
и всё, что приходит через узел доставки, зашифрованы долговременным ключом identity. Кто записал
трафик хаба или эфир и потом получит мнемонику, прочитает всю такую переписку. Сообщения через
Link защищены эфемерными ключами Link: там forward secrecy есть.

В обратную сторону всё в порядке: ratchet собеседника rns-net запоминает из его announce и
шифрует на него. У Python LXMF ratchet на адресе доставки включён всегда: 512 ключей, новый каждые
30 минут.

**Сделать.** Ratchet на своём адресе доставки, как у Python.

**Как.**

- **Вендоренный rns-net:**
  - свои ratchet-ключи (X25519) — на диске узла, новый раз в 30 минут, хранятся 512 последних;
  - announce с флагом контекста и ratchet-ключом;
  - входящие расшифровываются перебором своих ratchet, затем ключом identity — как
    `Identity.decrypt` с `ratchets` в Python.
- **lxmf-rs:** `announce_delivery` — с ratchet. `enforce_ratchets` не включаю: иначе перестанут
  доходить сообщения от клиентов без ratchet.
- **Несколько устройств** — пункт 3.6.

**Проверка.** interop-тест с Python:

- в announce есть ratchet (`Identity.get_ratchet` у собеседника);
- одиночный пакет и сообщение через узел доставки зашифрованы на ratchet и читаются;
- после смены ratchet старые сообщения ещё читаются;
- после перезапуска ключи на месте.

**Объём.** 4–6 дней.

### 4.3 Ответы, реакции и разметка по полям LXMF 1.1

**Сейчас.** bastyon-rns понимает поля картинки, файлов, голоса и данных Bastyon (`0xFB/0xFC`).
Поля LXMF 1.1 не поддерживаются:

- `FIELD_REPLY_TO` (0x30) и `FIELD_REPLY_QUOTE` (0x31) — ответы;
- `FIELD_REACTION` (0x40) — реакции;
- `FIELD_COMMENT` (0x41) и `FIELD_CONTINUATION` (0x42) — комментарии и продолжения;
- `FIELD_RENDERER` (0x0F) — разметка.

В LXMF-чатах нет ответов и реакций, хотя в таблице 6.5 анализа они помечены «беру». Ответ из
другого клиента приходит обычным сообщением без цитаты. Реакция без текста не показывается вовсе:
пустое сообщение `receiveLxmf` пропускает.

**Сделать.** Разбирать и отправлять эти поля; ответы и реакции — в LXMF-чате и в чате с маршрутом
(3.1). Разметку `RENDERER_MARKDOWN` показывать тем же безопасным рендером, что и остальной текст.
Какие поля шлют Sideband и MeshChat, проверить на их текущих версиях.

**Проверка.** interop-тест: Python-собеседник шлёт ответ и реакцию, и наоборот.

**Объём.** 2–3 дня.

### 4.4 Tor: хабы через SOCKS

**Сейчас.** В режиме Tor остаётся только RNode (`allowedInterfaces` в `reticulum-store.ts`). SOCKS
нет ни в bastyon-rns, ни в rns-net. Tor есть только в приложении для компьютера.

**Сделать.** TCP-интерфейс Reticulum через SOCKS встроенного Tor.

**Как.**

- Приложение запускает tor с `SocksPort 127.0.0.1:<порт>` (`src-tauri/src/tor/config.rs`).
- В вендоренном `rns-net/src/interface/tcp.rs` — необязательный прокси: SOCKS5 CONNECT без
  авторизации перед началом HDLC. Имя хаба разрешает Tor, поэтому работают и `.onion`-хабы.
  Переподключения тоже идут через прокси.
- Интерфейс поднимается после бутстрапа Tor.
- Локальная сеть (AutoInterface) в режиме Tor по-прежнему выключена.

**Проверка.** Режим Tor: хаб по имени и по `.onion`, переписка идёт; в `lsof -i` у процесса нет
соединений с адресом хаба.

**Объём.** 2–3 дня.

### 4.5 Интерфейсы: IFAC, TCP-сервер и остальные

**Сейчас.** Интерфейсы — только TCP-клиент, локальная сеть и RNode. Конфиг не пишет ключи IFAC.
Вендоренный rns-net уже разбирает `networkname`, `passphrase` и `ifac_size`, и в нём есть
интерфейсы TCP-сервер, UDP, I2P, KISS, Backbone и Pipe. Наружу ничего из этого не выведено.

**Сделать, по порядку:**

1. **IFAC** — имя сети и пароль у TCP и RNode. Без них не подключиться к закрытым сетям и части
   хабов.
2. **TCP-сервер на десктопе**, только в локальной сети. Телефон подключается к компьютеру по
   Wi-Fi там, где роутер режет multicast: в гостевых сетях и на многих роутерах. Вместе с 4.8
   компьютер становится шлюзом.
3. **KISS** — TNC пакетного радио. По запросу.

I2P — в разделе 12.

**Проверка.** interop-тест: Python `rnsd` с IFAC, с неверным паролем связи нет. Телефон работает
через TCP-сервер десктопа.

**Объём.** IFAC 1–2 дня, TCP-сервер 1–2 дня.

### 4.6 Защита от спама: штампы, блокировка, «только от знакомых»

**Сейчас.** Мой адрес доставки зарегистрирован без стоимости штампа. Списка блокировки нет,
сообщения принимаются от любого отправителя. Для чужих адресов, которые требуют штамп, узел его
считает. В lxmf-rs уже есть `ignored_list` и проверка штампов, но приложение их не использует.

**Сделать.**

- «Заблокировать» в меню LXMF-чата: `ignored_list` lxmf-rs, список хранится на диске узла.
- Настройка «Принимать только от знакомых»: от тех, с кем была переписка или есть маршрут.
- Стоимость штампа для входящих: по умолчанию 0; если пошёл спам — 8–16. Стоимость объявляется в
  announce.
- Билеты (`FIELD_TICKET`, 0x0C), чтобы знакомым не считать штамп, — как у Python LXMF.

**Объём.** 2–3 дня.

### 4.7 RNode по Bluetooth и на Windows

**Сейчас.** RNode подключается только через последовательный порт или файловый дескриптор. На
Android есть только мост USB (`RnodeUsbBridge.java`). На Windows RNode отклоняется, в интерфейсе
вместо формы пояснение.

**Как.** Один способ для обоих случаев. Радио-слой приложения уже умеет BLE (btleplug, очередь GATT
на Android) и USB (serialport работает и на Windows). RNode с Bluetooth отдаёт тот же поток KISS
через BLE-сервис последовательного порта — сверить по прошивке RNode. Байты передаются в
RNode-интерфейс rns-net потоком, а не через файл порта: в вендоренной копии интерфейс обобщается
до `Read + Write`. На Android так уже работает socketpair. На Windows socketpair нет, нужен канал
внутри процесса.

**Проверка.** Вживую (2.2): RNode с Bluetooth на macOS и Android, RNode по USB на Windows.

**Объём.** 4–6 дней.

### 4.8 Транспорт и свой узел доставки на десктопе

**Сейчас.** `enable_transport = No` и `share_instance = No` зашиты в конфиг узла. Своего узла
доставки нет.

**Сделать.** Выключатели на десктопе, по умолчанию выключены.

- **Транспорт.** Компьютер с RNode и интернетом ретранслирует между ними. Домашний телефон через
  него выходит на хабы, соседи по радио — тоже.
- **Узел доставки.** Сообщения для семьи и их телефонов ждут на моём компьютере, а не на чужом
  узле. lxmf-rs умеет роль узла доставки (`announce_propagation_node`), но насколько она зрелая
  (синхронизация между узлами, штампы), надо проверить против Python.
- Для узла доставки нужен предел места, в интерфейсе — трафик.

**Проверка.** interop-тест: Python-собеседник A в локальной сети, B — за TCP-хабом, они
переписываются через транспорт Bastyon. Python-отправитель кладёт сообщение на узел доставки
Bastyon, Python-получатель забирает его.

**Объём.** 1–1,5 недели.

## 9. Голос и звонки

### 9.1 Голос codec2

**Сейчас.** Входящее голосовое не в Opus показывается значком 🎤, без звука. Отправка — только в
Opus. Кода codec2 в приложении нет.

Для RNode Opus слишком тяжёл: 10 секунд даже на 6 кбит/с — это 7,5 КБ, а в codec2 700C — около
0,9 КБ. Поэтому для медленных каналов Sideband умеет слать голос в codec2, и такие голосовые в Bastyon
сейчас не играют.

**Сделать.**

- Приём: все режимы codec2 из LXMF (`AM_CODEC2_*`, 0x01–0x09) → PCM → WAV для плеера чата.
- Отправка: в codec2, когда маршрут идёт через RNode, или по выбору «голос для радио».

**Как.**

- Декодер и кодер на Rust — одни и те же для десктопа и Android (JNI). Проверить крейт `codec2`
  (порт на Rust): какие режимы он умеет. Если не все — C-библиотека codec2 через `cc`.
- Для отправки нужен PCM, а MediaRecorder даёт Opus. Запись идёт через WebAudio (AudioWorklet), и
  PCM уходит в Rust.
- Формат кадров — как у Sideband, сверить по его коду.

**Проверка.** interop: голосовое codec2, собранное кодом Sideband, проигрывается в Bastyon, а голосовое из
Bastyon декодируется там.

**Объём.** Приём 2–3 дня, отправка ещё 2–3.

### 9.2 Звонки LXST

В анализе звонки были вне объёма по двум причинам: лицензия LXST (CC BY-NC-ND) и отсутствие
реализации на Rust. Лицензия больше не препятствие, а Rust-реализации по-прежнему нет.

**Что потребуется.**

- Перенести LXST на Rust: сигнализация по Link, поток codec2 или Opus, буфер джиттера,
  эхоподавление.
- Звук — через cpal: он уже есть в приложении для голосового ввода. На Android — cpal или
  AudioRecord.
- Реально только по TCP, в локальной сети и на быстрых пресетах LoRa.
- Совместимость — с Sideband. Звонки MeshChat — другой протокол (раздел 12).

**Объём.** 3–5 недель. Делать после 9.1 и только если звонки действительно нужны.

## 12. Сознательно не делаю

- **Догружаемый модуль Reticulum** (раздел 7 анализа). Reticulum встроен и добавляет 3,6 МБ на
  Android. Отдельная загрузка с хэшами и своими обновлениями этого не окупает. Вернуться, если
  размер APK станет проблемой.
- **Matrix за адаптером `ChatTransport`.** Mesh подмешивается к Matrix, а путь Matrix не тронут —
  так меньше риска для рабочего мессенджера. Возможности сети (3.1) делаются и без этого.
- **Прочтения и «печатает» через mesh.** Каждое — отдельная передача, по LoRa это дорого.
  «Доставлено» есть.
- **Звонки MeshChat.** Они несовместимы с Sideband. Если делать звонки, то LXST (9.2).
- **MQTT Meshtastic.** Выводит трафик mesh в интернет через чужой брокер, а это против смысла
  mesh. В прошивке MQTT по умолчанию выключен, в интерфейсе его не показываю.
- **I2P-интерфейс Reticulum.** Нужен отдельный i2pd, а Tor уже есть (4.4).
- **Прошивка радио из приложения** (RNode, Meshtastic, MeshCore). Есть официальные
  веб-прошивальщики, а ошибка при прошивке может испортить плату.
- **iOS.** Приложение для iOS не выпускается. Если начнётся:
  - BLE — через CoreBluetooth;
  - Reticulum — тем же крейтом, статической библиотекой;
  - USB нет;
  - в фоне работает только BLE.
